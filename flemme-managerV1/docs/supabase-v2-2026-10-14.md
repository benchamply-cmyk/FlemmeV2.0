## Décisions

Une conversation possède une mission identifiée dès sa création. Messages, qualifications, erreurs, actions déclarées, résultats et transitions sont ajoutés à un historique horodaté UTC. Le statut est déduit des événements ; aucune ligne métier n'est remplacée. Les actions/résultats saisis sont des déclarations de l'utilisateur, pas la preuve qu'un agent a exécuté une action externe. Le Manager conserve sa capacité de qualification V1.1, sans nouvel outil externe.

Le message utilisateur est enregistré avant l'appel modèle. Un échec ajoute un événement générique et conserve ce message. Les identifiants UUID assurent l'idempotence ; une répétition terminée renvoie l'état sauvegardé sans appel modèle. Une répétition en cours renvoie 409. Une révision périmée renvoie 409. Les transactions SQL verrouillent la conversation pendant leurs écritures ; le verrou n'est pas tenu pendant un appel modèle.

Une analyse interrompue peut être libérée explicitement après cinq minutes. Son éventuel résultat tardif est enregistré avec late_result sans changer le statut actuel. Un nouveau message utilise un nouvel identifiant. Le contexte modèle reprend les messages enregistrés dans l'ordre, avec un plafond de 40 messages et 50 000 caractères ; dépasser ce plafond refuse l'analyse, conserve l'historique et demande de créer une nouvelle conversation. Aucune suppression ni compression destructive. Les règles locales de sécurité et de qualification des demandes autonomes restent prioritaires ; la continuité linguistique générale nécessite encore une validation modèle réelle.

## Accès

V2 est désactivée par défaut. Toutes ses routes vérifient une session Supabase avec e-mail confirmé, puis transmettent le jeton utilisateur aux RPC. RLS limite les lectures au propriétaire ; les RPC vérifient également ce propriétaire. Les écritures directes sont interdites aux rôles anon/authenticated ; seuls les RPC autorisés écrivent. Les fonctions auxiliaires sont privées et le search_path est fixé. Des triggers refusent UPDATE, DELETE et TRUNCATE, y compris les opérations accidentelles du propriétaire SQL. Un administrateur SQL capable de désactiver les triggers reste responsable de la conservation des données.

Quand FLEMME_V2_ENABLED=true, la route V1 /api/manager/analyze exige aussi cette session. Sans activation V2, le comportement V1 historique est conservé ; réserver alors son hébergement à un environnement contrôlé. Aucun jeton de service Supabase n'est nécessaire. Les diagnostics fournisseurs ne sont pas exposés ni conservés dans les événements. Le tracing du nouveau chemin conversationnel est désactivé.

## Configuration restant à réaliser

1. Exécuter manuellement `supabase/manager-memory-v2-20261014.sql` sur une base Supabase de préproduction. Le script est transactionnel, rejouable et crée uniquement le schéma fm_v2 et son RPC public. Il n'altère aucune table existante et n'ajoute pas de publication realtime, webhook ou synchronisation continue.
2. Configurer côté serveur FLEMME_V2_SUPABASE_URL (URL HTTPS du projet), FLEMME_V2_SUPABASE_PUBLISHABLE_KEY (clé publique ou anon), puis FLEMME_V2_ENABLED=true. Conserver ces réglages dans l'environnement de déploiement ; ne jamais employer une clé service_role.
3. OPENAI_API_KEY reste côté serveur. Une clé a été créée et enregistrée uniquement dans `.env.local` ignoré de ce checkout, avec accord explicite. Elle n'est ni copiée dans la PR ni dans les exemples. Depuis le répertoire flemme-managerV1, settings charge .env.local puis .env sans remplacer les variables déjà définies. Pour un déploiement, utiliser les variables serveur habituelles.
4. Installer avec `uv sync --locked --extra dev`, démarrer depuis flemme-managerV1 avec `uv run uvicorn flemme_manager.main:app`. Utiliser HTTPS en dehors de localhost. Le client transmet Authorization: Bearer avec sa session Supabase ; aucun owner_id fourni par le client.
5. Valider en préproduction deux comptes distincts, les sessions expirées et les reprises après redémarrage, puis raccorder le site à ces routes. Aucun déploiement, aucune exécution de migration distante, aucun appel OpenAI réel réalisés dans cette PR.

## Routes et utilisation

Toutes les routes ci-dessous utilisent la session utilisateur. GET /health reste public.

| Route | Corps ou résultat |
|---|---|
| POST /api/v2/conversations | conversation_id UUID fourni par le client ; création idempotente de la conversation et de sa mission |
| GET /api/v2/conversations?limit=20&offset=0 | liste paginée du propriétaire (100 maximum) |
| GET /api/v2/conversations/{id} | messages, événements, mission, révision, pending_request_id |
| POST /api/v2/conversations/{id}/messages | request_id UUID, expected_revision, request (1 à 5 000 caractères) |
| GET /api/v2/conversations/{id}/mission | identifiant, état, révision et événements |
| POST /api/v2/conversations/{id}/mission/events | request_id, expected_revision, kind status/action/result, note, state pour status, result pour result |
| POST /api/v2/conversations/{id}/messages/recover | identifiant de la requête interrompue, expected_revision, note ; après 5 minutes |

Les révisions peuvent avancer deux fois par analyse : ajout utilisateur puis qualification/échec. Lire la révision retournée avant la commande suivante. Le même request_id ne doit jamais servir à un contenu différent. Annuler est une transition d'état, sans suppression. Les missions terminées/annulées ne sont pas requalifiées. Le journal peut encore recevoir des annotations sans changer leur statut.

## Validation et limites

Tests Python hors réseau et tests SQL isolés, avec réponses modèle simulées. Les tests SQL utilisent PGlite 0.3.14 localement et PostgreSQL 16 dans GitHub Actions ; ce dernier ajoute un test à deux sessions concurrentes. Ils contrôlent l'isolation, les rôles, les révisions, les répétitions, les transitions, les erreurs, les résultats tardifs, la récupération explicite et la réapplication de la migration sur un historique rempli.

Ces tests ne valident pas une instance Supabase distante, le déploiement du site ou la qualité d'une réponse modèle réelle. Les sessions Supabase doivent rester valides durant les requêtes ; une expiration peut nécessiter de rafraîchir la session puis de relire l'état sauvegardé. Le schéma ne référence pas auth.users avec cascade : la suppression d'un compte n'efface pas cet historique. Toute politique de rétention future devra faire l'objet d'une décision distincte.

Reproduction SQL : `cd tests/sql && npm ci && npm test` pour PGlite. Pour PostgreSQL, utiliser une base vide isolée et SQL_TEST_DATABASE_URL avec un rôle de test capable de créer les rôles et le schéma auth simulé. Ne jamais exécuter le harness de test sur Supabase ou sur une base contenant des données réelles.
